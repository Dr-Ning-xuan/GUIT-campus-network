## v1.6.0 —— 彻底移除 ddddocr，两个模型全自训

### 新增

- **自训四位字母数字 CRNN**（`src/crnn4_ocr.py` 的 `Crnn4Solver`）
  - 输入 32×128（原生 80×24 RGBA），字符集 36 类 `0-9A-Z` + blank
  - 训练数据 10,599 张：raw4 两引擎一致 3,184 + raw4b 三票一致 7,415
  - 20 轮，最佳 val **98.11%**（上一版 92.77%）
  - int8 weight-only，**4.18 MB**
- **150 张人工标注验收集**（`label4_100` + `label4_50`），刻意排除在训练之外
- **三票预标注流水线**：自训模型 + ddddocr old + ddddocr slim 三引擎并行，
  三票一致 75.2%（7,516/10,000），作为训练集；两票/一票的 2,484 张留给后续人工

### 移除

| 移除项 | 打包占用 | 移除理由 |
|---|---|---|
| `common_slim.onnx` | 18.36 MB | 算式旧兜底，CRNN 已接管 |
| `common_old.onnx` | 6.46 MB | 4 位官方模型，被 captcha4 替代 |
| `ddddocr` 包本体 | 0.15 MB | 两个模型都不再需要 |
| `MathCaptchaSolver` 的 ddddocr 回退分支 | — | 加载失败改为直接抛错，不再假装能救 |
| `_install_cv2_stub` 的运行时必要性 | — | 只服务 ddddocr 的 cv2 硬 import |

### 修复

- **自检文案造假**：`main.py` 里一直打印 `[selftest] ddddocr 4位 OK`，
  实际早就不走 ddddocr 了。改为打印真实类名（`Crnn4Solver`）
- **测试与产物脱节**：`test_portal.py` 拿 `CaptchaSolver(length=4)` 测 `normalize`，
  测试里 ddddocr 还在、产物里已经没了。改用 `Crnn4Solver`
- **spec 打包整个 models/ 目录**：备份和实验模型会被一起打进去。改为逐文件列举

### 提升

| 指标 | v1.5.1 | v1.6.0 | 变化 |
|---|---|---|---|
| **exe 体积** | 82.75 MB | **60.92 MB** | −21.83 MB（−26%） |
| **4 位准确率**（150 张人工） | 71.3%（ddddocr old） | **96.0%** | **+24.7 pt** |
| 4 位模型体积 | 51 MB / 20 MB | **4.18 MB** | 小 5~12 倍 |
| 4 位单图耗时 | ~1100 ms | **7 ms** | 快 157× |
| 算式准确率（新 100 张） | 68.0% | **70.0%** | +2.0 pt |
| 打包条目数 | 477 | **439** | −38 |

## v1.5.1 —— 换自训 CRNN，算式识别从 36% 到 66%

### 新增

- `src/crnn_ocr.py` 的 `CrnnSolver`：21 类 CRNN（`0-9 + - × ÷ = ? 加减乘除`）
  - 骨干 64/128/256/256 + BiLSTM 256，约 620 万参数，输入 **96×320**
  - 训练数据：4.5 万张/轮几何增广合成图 + 2.3 万张真图（ddddocr ≥5 票自举）
  - 11 epoch / RTX 5060 / 49 分钟，导出 int8 **6.3 MB**
- `single_shot` 机制：`CrnnSolver.single_shot = True`，`service.py` 见到它直接把票数门槛强制归零

### 移除

- 算式识别不再用 ddddocr 的多引擎投票（72 类字符集里没有 `÷`，除法 30 张全错）

### 修复

- **票数门槛在升级后仍然生效**：老用户 `config.json` 里存着 3 或 5，
  结果每张图都被判「票太少不提交」，一路换到第 30 张才被迫提交最差的那张。
  现在由 `single_shot` 强制归零，老配置不用改

### 提升

| 指标 | v1.4.3（ddddocr） | v1.5.1（CRNN） | 变化 |
|---|---|---|---|
| 单图算对 | 36.0% | **66.0%** | +30.0 pt |
| ＋ | 43.8% | 50.0% | +6.2 |
| － | 33.3% | 59.3% | +26.0 |
| × | 76.9% | 69.2% | **−7.7**（没藏） |
| ÷ | 0.0% | **80.0%** | +80.0 |
| 单张耗时 | ~1002 ms | **20 ms** | 快 50× |

**代价**：78.1 → 82.7 MB（模型 4.5 → 6.3 MB）。

### 已知缺陷（没藏）

- 个位题（＋ 类）只有 50%，典型是 `77+0` 读成 `7+0`（首字符被 CTC 吃掉）
- `×`/`÷` 偶有混淆

## v1.4.3 —— 认出率 67% → 80%

### 新增

- 2× 放大档（小图放大后模型对粘连字符分辨更好）
- 早停：3× 那批票数够了直接返回

### 修复

- **变体分配导致结果漂移**：以前 24 个变体按 `i % 2` 分给两个模型，
  同一变体只有一个模型看过，认出率随变体顺序在 71%~79% 浮动。
  改成两个模型都看每个变体，票数翻倍、结果确定

### 提升

- 认出率 67% → **80%**
- 5 张内登录成功 89% → **94%**
- ≥5 票的图 33 → **60 张**
- 平均每张 737 ms

## v1.4.1 —— 模型裁到 19.8 MB，exe 再瘦 28.5 MB

### 移除

| 移除项 | 大小 | 理由 |
|---|---|---|
| `opengl32sw.dll` | 19.7 MB | Qt 软件 OpenGL 兜底，本程序只用普通控件 |
| Pillow `_avif.pyd` | 7.5 MB | 验证码是 PNG，永远走不到 AVIF |
| `common.onnx` 的 8,210 类输出层 | 51.6 → 19.8 MB | 只用到 72 类 |

### 修复

- **版本资源从来没进过 exe**：`tools/make_version.py` 生成了 `version_info.txt`，
  但 `app.spec` 里两个 `EXE()` 都没传 `version=`，exe 属性里 `FileVersion` 一直是空的

### 提升

- 129.6 → **101.1 MB**
- 裁剪后与原版**逐字节一致 8/8**（零精度损失，不是「效果差不多」）

### 踩过的坑

- CTC 的索引 0 是 blank token，裁类别时必须留下它并让它稳稳待在第 0 位。
  否则 `if idx != 0` 会把被移过来的真实字符当 blank 吃掉

## v1.4.0 —— 送走 112 MB 的 OpenCV

### 移除

| 移除项 | 大小 | 理由 |
|---|---|---|
| OpenCV (`cv2`) | 112 MB | 全项目只用了 `cvtColor` 和 `morphologyEx` |
| `common_det.onnx` | 19.2 MB | 目标检测模型，只调 `classification()` 永远走不到 |
| ddddocr 重复引擎 | — | `DdddOcr(old=True)` 和默认参数加载的是**同一个** `common_old.onnx` |

### 新增

- `_install_cv2_stub()`：ddddocr 的 `slide_engine` 在模块顶层硬 import cv2，
  cv2 不存在时直接抛 ImportError。往 `sys.modules` 塞空壳让它平安过去

### 修复

- **形近字母还原**：ddddocr 常把 1 认成 I、0 认成 O、5 认成 S，
  老代码 `_STRIP_RE` 一律剥掉字母 = 把数字吃掉了。改为只收大写还原
  （小写 l/i 绝不能碰，它们多半是「加」「减」被认歪的偏旁）
- **拒绝前导零**：`8-02` 这种题门户不会出，出现基本是多认了一位

### 提升

- 189.1 → **129.6 MB**（−31%）
- 冷启动 6.9 s → **3.4 s**
- 单张识别 464 ms → **301 ms**
- 离线 60 张认出率 78% → **82%**

### 试过但没用（别再试）

- 裁剪窗口右移：认出率涨到 83%，但**服务端通过率从 53% 掉到 44%** —— 多认出来的基本是多认了一位
- 连通域分割：块数分布 {2:1, 3:8, 4:7, 5:7, 6:5, 7:1, 8:1}，干扰线把字连成一片，切不齐

## v1.3.1 —— 把识别率从 8% 拉到 43%

### 新增

- 「更新地址」按钮（开浏览器到 GitHub 仓库）
- 托盘加固：唤出时确认图标还在、托盘不可用写日志
- **7 个调参工具**：`grab_captcha` / `montage` / `eval_offline` / `score` / `exp_ocr` / `debug_one` / `peek_variants`

### 修复

三处根因：

1. **二值化用错通道**：原来按「RGB 最大通道 < 阈值」取前景，
   深蓝/深紫字符 B 通道 200+ 被判成「亮」丢掉。换成感知亮度
   `0.299R+0.587G+0.114B` 后，深色字符（灰度 100~160）与亮彩色干扰（190~230）一下分开了
2. **右边 `= ?` 被一起喂给模型**：问号在不少字形里就是个「2」，
   `8乘6=?` 被读成 `8*62 = 496`
3. **没裁边**：200×60 里字符只占中间一小块，缩放后只有二十几像素高

### 提升

| 指标 | v1.3.0 | v1.3.1 |
|---|---|---|
| 认出率 | 45% | **78%** |
| 单图可用 | 8% | **43%** |
| 单张耗时 | 1.07 s | **0.47 s** |

- 换一批全新 120 张复测：认出 **95/120 = 79%**，两批数字对得上
- 假账号走真门户 40 张：认出 73%，提交 11 次，服务端认 6 次 = **55%**
  （不带票数过滤那轮：提交 12 次只对 4 次 = 33%）

## v1.3.0 —— 门户换验证码了

### 新增

- **支持 `/ACaptcha.ashx` 算式验证码**（原来是 `/CheckCode` 的 4 位字母数字）
- 32 个预处理变体 × 3 个模型 = 96 次识别，三线程并行
- **手动兜底**：识别彻底失败时弹窗让人填（`manual_captcha` 默认开）
- 压测工具 `captcha_bench.py` 支持 `--kind math/old` 与 `--verify`

### 修复

- **关了之后再双击打不开**：点 × 只收进托盘，进程没退、单实例锁还在，
  再双击时旧代码 `print` 一句就 `return 0`，而 `--windowed` 没有控制台 → 用户看到「双击没反应」
- **单文件版双击没反应**：`%TEMP%` 里堆了 **66 个 `_MEI*` 残留目录**，
  PyInstaller bootloader 清理/创建临时目录时卡死
- **唤醒出来的窗口一片空白**：`EnumWindows` + `ShowWindow` 只拉出 Win32 外框，
  Qt 内部仍认为自己是隐藏状态，一个字都不画

### 提示

- 根因是**从源头就取错了**：老版本拿的是注销页那张图，和登录页的答案根本不是一回事

## 附：识别率的计量口径（这一路最大的教训）

| 阶段 | 当时自称的「准确率」 | 真实「答案算对」 | 差在哪 |
|---|---|---|---|
| v1.3.x | 认出率 78% | 单图可用 43% | 认出来 ≠ 算对 |
| v1.4.x | 认出率 80% | **36.0%** | 吐出合法算式 ≠ 答案对 |
| v1.5.1+ | **答案算对** | 66.0% | 口径统一了 |

**认不出只是换张图（不要钱），认错要提交一次账号。**
所以从那之后所有验收都只认「提交上去服务端说对的次数」，不再看中间指标。
